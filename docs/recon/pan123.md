该 APK 是 Flutter 应用，业务 URL 全部集中在
`assets/flutter_assets/assets/config/interface_config.json`。

- 接口总数 **220**，全部在 `interfaceapi` 对象里，基址 `https://api.123278.com`。

  `{"code":401,"data":null,"message":"cookie token is empty",...}`，

## 推断（需真实账号验证，代码里已隔离在 Pan123Api 一处）

- 登录成功后返回 `data.token`，后续请求头用 `Authorization: Bearer <token>`。
- 文件列表参数：`driveId=0&limit&next&orderBy&orderDirection&parentFileId&trashed=false&category=0`，
  返回 `data.Next`（空串表示没有下一页）与 `data.InfoList`。
- `InfoList[].Type`：`0` = 文件，`1` = 文件夹。
- 上传走 S3 预签名：`upload_request` 拿 `servers`/预签名 URL，分片 PUT 后
  `upload_complete` 收尾。

## 上传流程（来自 OpenList `drivers/123/upload.go`，已实现）

1. **先算 MD5**。`upload_request` 的请求体：
   `{driveId:0, duplicate:2, etag:<小写 md5>, fileName, parentFileId, size, type:0}`。
   `duplicate` 2 = 覆盖同名、1 = 自动重命名、0 = 服务端默认。
2. **响应有三种形态**：
   - `data.Reuse == true` 或 `data.Key` 为空 → 秒传，**一个字节都不用传**；
   - `AccessKeyId`/`SecretAccessKey`/`SessionToken` 都非空 → 官方 App 用 S3 SDK 直传，
     我们不用这条（省掉整个 AWS SDK）；
   - 其余 → 用 `Key`/`Bucket`/`StorageNode`/`UploadId`/`FileId` 走预签名分片。
3. **分片大小 16 MiB**，片数 `ceil(size/16MiB)`，最后一片是余数。
4. **取签名分两个端点**（用错拿不到 URL）：
   - 单分片 → `/api/file/s3_upload_object/auth`
   - 多分片 → `/api/file/s3_repare_upload_parts_batch`，一次最多 10 片

   请求体统一：`{StorageNode, bucket, key, partNumberStart, partNumberEnd, uploadId}`
   （注意前两个 Key 大写、其余小写，这是服务端的原样字段名）。
   响应：`data.presignedUrls` 是 `{"1": "https://..."}` 形式的 map，键是分片号（从 1 开始）。
5. **PUT 到预签名 URL 时不能带 Authorization 头**，签名在 query 里，多一个鉴权头会被判签名不匹配。
   返回 403 时应当重新取一次该批签名再重试（OpenList 用 singleflight 去重）。
6. **收尾** `POST /api/file/upload_complete/v2`，body：
   `{StorageNode, bucket, fileId, fileSize, isMultipart, key, uploadId}`。
   `isMultipart` 是 `chunkCount > 1`。

本项目在 `provider/pan123/.../Pan123Uploader.kt` 实现，未走 S3 SDK 分支（避免引入 AWS SDK）。
- 风控：密码登录可能要求图形/短信验证，暂以「Token 导入」作为兜底登录方式。

## 风险

- 官方随时可能加签名或改字段；所有 DTO 都集中在 `Pan123Dto.kt`，改一处即可。
- 分享功能涉及风控，先只支持「创建无密码分享」。

## 打开别人的分享并转存（已实现）

链路三条端点全部来自 APK 内 `interface_config.json`：
`shareFileDetails = /api/share/get`、`copySaveFiles = /restful/goapi/v1/file/copy/save`、
`copySaveTask = /restful/goapi/v1/file/copy/save/get`。

**列分享目录** `GET /api/share/get`（匿名即可，不需要登录）：

```
limit=100&next=0&orderBy=file_name&orderDirection=asc
&shareKey=<shareKey>&ParentFileId=<父 id，根目录 0>&Page=<从 1 起>
[&SharePwd=<提取码>]
```

- 大小写是混的：`ParentFileId` / `Page` / `SharePwd` 首字母大写，其余小写。
- **没有提取码时整段 `SharePwd` 都不能出现**：发空值会被服务端判成参数缺失。
- `next` 固定发 `0`，翻页只靠 `Page` 递增。
- 响应 `data.Next` 的终止值是字符串 `"-1"`；**空串表示还有下一页**，
  所以判断条件只能是 `next != "-1"`，不能用 `isNotBlank()`。
- 响应 `data.Expired == true` 表示分享已失效。

实测（2026-11-23，无凭证）：`GET /api/share/get` 缺参数时的报错链是
`请输入ParentFileId` → `请输入Limit` → `请输入OrderBy` → `请输入OrderDirection` → `请输入Page`，
齐全后返回 `{"code":5103,"message":"此分享不存在"}`；
`shareKey` 裸值（`abcde`）返回 `{"code":400,"message":"ShareKey格式异常"}`，
形如 `abcde-fghij` 才被接受。这些说明端点是真实存在的，参数校验在业务校验之前。

**转存** `POST /api/restful/goapi/v1/file/copy/save`（**必须登录**，匿名一律
`{"code":401,"message":"cookie token is empty"}`）：

```json
{
  "fileList": [{
    "fileID": 11, "fileId": 11, "size": 2048, "etag": "...",
    "type": 0, "parentFileID": 88, "parentFileId": 88,
    "fileName": "资料.zip", "driveID": 0, "driveId": 0,
    "s3keyFlag": "1816216065-0", "S3KeyFlag": "1816216065-0", "StorageNode": "..."
  }],
  "shareKey": "abcde-fghij",
  "sharePwd": "1234",
  "currentLevel": 1,
  "superAdmin": null
}
```

- `fileList` 里每一项都**大小写两套字段名一起带**，服务端不同网关取的不是同一个。
- `s3keyFlag` / `etag` / `StorageNode` 三个值来自分享列表项的
  `S3KeyFlag` / `Etag` / `StorageNode`；本项目把它们拼成
  `flag|etag|node` 一个票据存在 `ShareEntry.ticket` 里。
- 没有提取码时 `sharePwd` 发空串 `""`，不能发 `null`。
- `parentFileID` 是**自己的网盘**里的目标目录 id，根目录为 `0`。

**轮询** `GET /api/restful/goapi/v1/file/copy/save/get?taskID=<id>`：

- 参数名是大写 `taskID`（网页端原文
  `"/restful/goapi/v1/file/copy/save/get?taskID=".concat(e)`）。
- 完成判据没有统一标志，要同时认：`finished == true`、`status` 为 2 或 3、
  `state` 为 `success`/`done`、或响应里出现 `fileId`/`FileId`/`newFileId`。

**请求体字段的证据强度**（写在这里免得以后误以为是抓包得来的）：
- 端点路径、`taskID` 参数名、`sharePwd` 空串约定、`operation` 语义：
  来自分享页 bundle `statics.123pan.com/assets/js/index.587d64af.js`（原文已核对）。
- `fileList` 里的大小写双份字段与 `currentLevel`/`superAdmin`：
  来自公开实现交叉验证（CYQawa/YunX `Pan123Api.copySave`、mengangs/Cloudn
  `Pan123.copySaveEntry`、walkingddd/TgtoDrive `tgto123.py`），三者一致，
  但**不是**从 APK 直接读出的。
- `lib/arm64-v8a/libapp.so` 里能搜到 `copySaveFiles` / `copySaveTask` /
  `shareFileDetails` / `taskID` / `fileIds` / `SharePwd` / `ShareKey` 等符号，
  但都是 Dart 符号表里的标识符，没有请求体上下文。

**分享链接形态**：`https://www.123pan.cn/s/<shareKey>?pwd=<提取码>`，
域名历史上有 123pan.com / 123pan.cn / 123865.com / 123912.com / 123684.com 多种，
shareKey 形如 `abcde-fghij`（5 位-5 位，含连字符）。

## 搜索

**没有独立的搜索端点。** 文件搜索就是把普通列表请求 `GET /api/file/list/new`
的 `searchData` 填上关键字，再加一个 `isSearchOrder=true`：

```
GET /api/file/list/new
  ?driveId=0&limit=100&next=0
  &orderBy=file_name&orderDirection=asc
  &parentFileId=0&trashed=false&category=0
  &searchData=<百分号编码的关键字>
  &type=0
  &isSearchOrder=true&timeMode=0&inDirectSpace=false
```

- `parentFileId=0` 表示**全盘搜索**（网页端 `"fullSearch"===e?0:"currentFolder"===e?Q:0`），
  填当前目录 id 就只在那个目录里搜。
- `searchData` 必须自己百分号编码。表单编码会把空格写成 `+`，服务端当字面量加号，
  带空格的关键字永远搜不到。
- 不带上 `isSearchOrder`，服务端就退回普通列表，关键字等于没写。
- 响应仍是 `data.InfoList` / `data.Next` / `data.Total`。
- **游标终止值有两个**：`"-1"` 与 `"0"`（结果为空时服务端回 `"0"`）。只判 `-1`
  会让结果页多显示一次「加载更多」，点下去拿到同一批空数据。
- 搜索结果条目多两个字段：`ParentName`（所在目录名）与 `StarredStatus`。
  `HighLight` 是**带高亮标记的同一份文件名**，不能拿来当名字用，
  否则列表上会出现一堆标记串——仍然取 `FileName`。
- 排序取值域：`orderBy` ∈ {`file_name`, `size`, `update_at`, `update_time`}，
  `orderDirection` ∈ {`asc`, `desc`}（网页端还认 `a-z`/`z-a`/`newest`/`oldest`）。

**另一条容易混淆的路径**：`GET /api/restful/goapi/v1/file/search/app/list`
（网页端 `searchAppList`）是搜索**建议**，不是文件搜索，本项目未使用。

**证据强度**：以上全部来自 APK 内
`assets/flutter_assets/assets/web_res_123/static/js/main.bba88759.js` 的原文
（`Gr(e){return Ce.get("file/list/new",{params:e,skipResponseHandler:!0})}`，
参数体在 `Nr=` 函数里），**不是抓包也不是推断**。端点探测（无凭证）返回
`{"code":20101,"message":"未登录"}`，对照 `/api/file/list/nope` 是纯文本 `404 Not Found`。


## 回收站（已实现）

123 云盘没有独立的回收站接口：**列表还是普通列表，靠 `trashed` 与 `event` 切过去**。

### 列表

```
GET https://api.123278.com/api/file/list/new
  ?driveId=0&limit=100&next=0
  &orderBy=trashed_at&orderDirection=desc
  &trashed=true&parentFileId=0
  &event=recycleListFile
```

- 网页端调用点：`Gr({Page:t, limit:r, orderBy:n, orderDirection:a,
  event:"recycleListFile", trashed:!0, parentFileId:0, driveId:0})`。
- 排序取值：`deleteTime` → `trashed_at`、`fileSize` → `size`，
  默认 `{field:"deleteTime", order:"desc"}`（最新删的在前）。
- 游标终止值仍是 `"-1"` 与 `"0"` 两个，走 `Pan123Wire.nextCursor`。
- 条目多两个字段：`TrashedAt`（可能缺）与 `TrashedExpire`。
  网页端显示的删除时间是 `TrashedAt || UpdateAt` 兜底，本项目照抄这个规则；
  `TrashedAt` 缺失时宁可显示「删除时间未知」，不编一个时间出来。
- 文件夹判定与普通列表一样看 `Type === Folder`。

### 放进回收站（普通删除）

```
POST https://api.123278.com/api/file/trash
{"driveId":0,"operation":true,"event":"intoRecycle","operatePlace":1,
 "RequestSource":null,"fileTrashInfoList":[{"fileId":7}]}
```

`operatePlace`：单选 `1`，多选 `2`。确认框文案「可在回收站中找到已删文件」。

**这是本项目改过的一处语义**：最初文件列表里的删除打的是 `/api/file/delete`
（永久删除），也就是点一次删除就真的没了。现在走 `file/trash`，
`file/delete` 只留给回收站里的「彻底删除」。

### 还原到原位置

同一个 `file/trash` 端点，换参数：

```
POST https://api.123278.com/api/file/trash
{"driveId":0,"operation":false,"event":"recycleRestore","operatePlace":1,
 "RequestSource":null,"fileTrashInfoList":[{"fileId":7}]}
```

- **响应里有坑**：原目录已经不存在时服务端不报错，而是在
  `data.AbnormalFileIdList` 里列出没还原成功的 id。网页端提示
  「部分文件还原失败，父级不存在。失败文件ID: …」。
  只看 `code` 会告诉用户「已还原」而实际有一项没动。

### 还原到指定目录

```
POST https://api.123278.com/api/file/recover/by_path
{"fileIds":[7],"parentFileId":99}
```

`fileIds` 是**数字数组**（网页端 `Rr({fileIds: r.map(e=>e.FileId), parentFileId:t})`，
`FileId` 本身是数字），与 `file/trash` 里 `{"fileId":7}` 的对象数组不同。

### 彻底删除

```
POST https://api.123278.com/api/file/delete
{"fileIdList":[{"fileId":7}],"operatePlace":1,"event":"recycleDelete","RequestSource":null}
```

网页端还会带可选 `vCode`（有验证码时），本项目目前不带。

### 清空回收站

```
POST https://api.123278.com/api/file/trash_delete_all
{}
```

网页端是 `Jr(tS({}, t && {vCode:t}))`，`tS` 是 `Object.assign` 包装，
无验证码时等价于只传 `{}`。

### 端点存在性

无凭证探测：`GET /api/file/list/new?...&trashed=true&event=recycleListFile`
与 `POST /api/file/trash`、`POST /api/file/delete`、`POST /api/file/recover/by_path`
都返回 `{"code":20101,"message":"未登录"}`；对照 `POST /api/file/definitelyNotRealXYZ`
是纯文本 `404 Not Found`。两种失败形状不同，所以 20101 能证明端点存在。

### 证据强度

路径来自 APK 内 `assets/flutter_assets/assets/config/interface_config.json`
（`recycleDeleteFile` / `trashDeleteAll` / `fileRecoverByPath` / `deleteFile` 四条），
请求体来自 APK 内网页 bundle `assets/flutter_assets/assets/web_res_123/static/js/main.bba88759.js`
的原文（`Vr`=file/trash、`Rr`=file/recover/by_path、`Xr`=file/delete、
`Jr`=file/trash_delete_all），并与开源实现 OpenList `drivers/123/driver.go` 的
`Remove` 交叉验证一致。**不是抓包也不是推断。**

### 只做 123 一家

百度 App 里确实有回收站（安装包里有 `RecycleBinActivity`、
`RecycleBinFileListParser`、`RestoreRecycleBinClearedFilesJob` 等业务类），
但端点路径不在 dex 明文里（被混淆或服务端下发），取不到就不硬猜；
夸克安装包里搜不到这类接口。所以 `capabilities.trash` 目前只有 123 云盘声明为 true。
