# PanHub

一个统一管理多家网盘文件与分享的 Android 客户端。

- **Kotlin + Jetpack Compose** 写界面与业务
- **Rust** 写共享内核（摘要、分片校验等重活），通过 JNI 暴露窄接口
- **构建只在 GitHub Actions 上跑**，本地不编译

## 设计原则

1. **深模块化**：模块只通过窄接口交互。\`:core:*\` 是契约，\`:provider:*\` 是实现，
   \`:feature:*\` 是界面，\`:app\` 只做组装。新增一家网盘 = 新增一个 provider 模块
   + 一行注册，不动任何界面代码。
2. **能力声明而非类型判断**：每个 provider 声明 \`ProviderCapabilities\` 与 \`AuthMethod\`，
   UI 据此隐藏按钮、决定登录表单形态，杜绝 \`if (provider == "xxx")\` 这类耦合。
3. **错误归一化**：所有 provider 操作返回 \`PanResult\`，网络/鉴权/限流/不支持
   都映射成统一的 \`PanError\`，UI 只处理一种错误类型。
4. **UI 参考蓝云**：冷调蓝紫主色、浅冷灰背景、白色圆角卡片。

| \`:core:model\` | 纯数据模型：RemoteNode / Quota / ShareLink / ProviderCapabilities / AuthMethod |
| \`:core:common\` | PanResult / PanError / DispatcherProvider / Clock / FileDigest |
| \`:core:network\` | OkHttp 封装、Cookie 存储、流式请求体，唯一的 HTTP 出口 |
| \`:core:design\` | 蓝云风格 Compose 主题、间距规范与公共组件 |

| \`:core:transfer\` | 上传/下载队列、整目录上传与下载、跨网盘转存与整目录复制（串行执行、可暂停与取消、断点续传、队列存档、网络抖动自动退避重试） |
| \`:core:kernel\` | Rust 内核 + JNI 桥接（MD5/SHA1/SHA256/CRC32、分片 MD5、上传摘要一次扫描） |

| \`:provider:api\` | PanProvider 接口 + ProviderRegistry + ScopedPanProvider + UploadSource |

| \`:provider:baidu\` | 百度网盘（含 4MiB 分片上传与秒传、分享转存） |
| \`:feature:accounts\` | 账号列表与登录 |
| \`:feature:browser\` | 文件浏览与操作 |
| \`:feature:transfers\` | 传输队列界面 |
| \`:feature:shares\` | 我的分享：按账号列出已创建的分享链接 |
| \`:feature:shareimport\` | 打开别人的分享、挑文件转存到自己网盘的任意目录 |

跨网盘转存不需要服务商提供额外接口：源端取下载直链、目标端走上传，
任何同时支持下载与上传的两个账号之间都能转存。中间文件落应用缓存目录，
传完即删。

上传前的摘要计算走 \`:core:kernel\` 的 \`scan_file\`：一遍读盘同时算出整文件
MD5、SHA-1、前缀 MD5 与逐分片 MD5，四家网盘各取所需。没有 NDK 产物时
（本机调试构建）\`KernelUpload.scanner()\` 返回空实现，各 provider 自动退回
自己的 Kotlin 实现，所以「有没有内核」不影响正确性，只影响大文件的准备时间。

复制整个文件夹时，先在目标账号里按原层级把空目录逐层建出来，再把每个文件
当成一次普通的转存排进队列；目标账号必须支持新建文件夹。已经在目标端建好的
目录不会因为中途失败被回滚——目标端没有通用的批量删除，硬清理反而有风险。

下载整个文件夹时会先排一个「整理文件列表」的任务，把目录逐层列完再放出
每个文件的下载任务，本地按原来的层级还原（同名文件夹不会被摊平成一个）。

夸克网盘的上传走阿里 OSS：先向夸克要一张上传票据，把 MD5 与 SHA-1 报过去
（命中已有文件就直接秒传），再逐片换 OSS 签名往预签名地址 PUT，最后先合并
分片、再通知夸克索引。签名串多一个换行都会被判不匹配，所以那部分单独放在
`QuarkOss` 里并有逐字的单测。

夸克网盘的分享是异步的：创建接口只返回一个任务号，要轮询任务拿到分享
id，再换一次链接接口才有能发出去的地址与提取码。有效期服务端只有
永久/一天/一周/一月四档，用户选 3 天只能落到一周档，所以界面显示的是
实际到期时刻而不是用户填的天数。分享列表、取消分享也走同一套接口。

夸克网盘的「打开别人的分享」是一条独立链路：先用 pwd_id 换 stoken（分享的
访问票据），再按目录逐页读条目，每个条目额外带一个只对本次分享有效的
取件凭据；转存时把这些凭据和 fid 一起提交，服务端再起一个异步任务。
所以转存成败要轮询任务号才知道，完成数取服务端返回的 save_as 计数，
而不是请求里的条数——分享里的文件超过 100 个时，服务端只回前 100 个 fid。

123 云盘的「打开别人的分享」不需要先换票据：分享列表接口匿名就能读，
提取码直接作为参数带上（没有提取码时整段参数都不能出现，发空值会被判参数缺失）。
转存是登录后才能做的事，服务端只回一个任务号，要轮询到完成为止；
提交时每个条目都要带 `S3KeyFlag`/`Etag`/`StorageNode` 三样，
所以列表阶段就把它们拼成一个票据存进 `ShareEntry.ticket`。

123 云盘的分享列表还有个坑：`Next` 的终止值是字符串 `-1`，但空串表示「还有下一页」，
所以判断条件只能是 `!= "-1"`，写成 `isNotBlank()` 会永远停在第一页。

转存的目标目录默认是自己的网盘根目录，列表顶部那行「转存到 …」点开可以换。
选目录用的是各家都有的普通文件列表接口（只看文件夹），所以三个支持转存的
服务商共用同一套界面；换目录是浏览过程中的一个短暂动作，用对话框而不是新页面，
取消之后还留在原来的分享目录里。

天翼云盘的上传在另一条加密通道上（upload.cloud.189.cn）：每个请求都要把
表单做 AES-ECB 加密、再用 HMAC-SHA1 签名，随机密钥本身用服务端下发的 RSA
公钥加密后放进请求头。文件大于 10 MiB 时要额外报一个「分片摘要」——把每片
MD5 的大写十六进制用换行连起来再取一次 MD5；服务端据此判断能否秒传。
细节在 docs/recon/cloud189.md，纯字符串与摘要逻辑有单测。

官方客户端还有一条自己的通道（api.cloud.189.cn），每个请求都用
sessionSecret 做 HMAC-SHA1 签名，不需要 Cookie。这条通道在项目里已经实现成
可插拔的一层，但**默认不启用**：换会话与刷新 token 都要真实 accessToken 才能
验证，没有账号时切过去只会把现在能用的 Cookie 通道弄坏。预留层把「换会话 /
刷新 token / 签名请求 / 会话失效自动重试一次」四件事都写好并用脚本化响应测住，
将来有账号时只要把 provider 的调用点换过来。

百度网盘的上传要报三个摘要：整文件 MD5、**前 256 KiB** 的 MD5、以及每片的
MD5 列表。分片字节走 d.pcs.baidu.com 的 superfile2（域名由 locateupload
换发，这个接口不需要认证），收尾再由 xpan/file 的 create 合并。秒传判定在
precreate 的 return_type 里，等于 2 就直接拿到文件元数据。分片大小按非会员的
4 MiB 切，会员账号同样可用，只是片数更多。

上传整个文件夹是同一套思路反过来：先在网盘里按本地层级把目录建出来，
再把每个文件当成一次普通上传排进队列。空文件传不上去，会在整理阶段跳过
并在进度里写明跳过了几个；整棵树都是空文件时会说清楚是「空文件夹（跳过
N 个空文件）」，而不是假装什么都没发生。

传输期间会起一个前台服务（dataSync 类型），通知栏常驻一条进度，
说的永远是「现在在传什么、还剩多少」。它的作用不是好看：手机上的后台
进程随时会被回收，几 GB 的下载传到一半被杀掉，用户回来只看到队列卡住。
只在队列里有活的时候启动，传完自己停，不会留一个空壳在后台。

传输遇到断网、限流、服务端 5xx 会自动重试（默认 3 次，1 秒起翻倍退避），
退避期间任务让出队列，后面的文件可以先传。鉴权过期、文件不存在这类
重试无意义的错误直接失败，让人早点看到真正的原因。

传输队列会存档：进程被杀掉、手机重启之后队列还在，上次没跑完的任务自动接着跑
（下载靠 `.part` 续传，上传与转存重来一遍）。存档坏了只会丢掉历史，不影响启动。

下载断点续传：没下完的文件留在 `.part` 里，下一次用 `Range` 只补剩下的部分。
服务端忽略 `Range` 回 200 时不会把整份内容追加到旧残片后面（那样文件就毁了），
而是从头写；残片比目标还大则直接丢掉。只有「区间不存在」（416）才认为是链接失效，
丢掉残片重来，网络错误一律保留残片等下次。


传输页标题会带上整体进度：队列里有几项在跑、已经搬完多少字节、大概到几成。
没有总数（比如上传时还不知道目标端要写多少）就只显示任务数，不编一个百分比出来。

正在传的那一项会显示实时速率和剩余时间，速率按最近 5 秒的采样算。
速率要至少两个采样点、跨度满 0.5 秒才报，刚起步的瞬间什么都不显示
（写「0 B/s」会让人以为卡住了）；排队中的任务、已经结束的任务、以及只搬列表的
整理型任务都不显示速率。剩余时间向下取整，宁可说少了也不让人以为还要等更久。

正在传和排队中的任务都能暂停，暂停之后可以继续。暂停与取消的差别只在磁盘上：
取消会把没下完的 \`.part\` 删掉，暂停留着它——下次继续时用 \`Range\` 接着传，
不用从头再来。暂停的任务不占执行位，队列里后面的任务会顶上来；
它保留原来的位置和已传字节数，恢复时不会跑到队尾，也不会显示成从零开始。
正在退避等待重试的任务同样能暂停，那个计时器会一起停掉，否则几秒后它自己又跑起来了。

阿里云盘按设计不接入：两条接口路线分别要开放平台密钥和设备签名，
与本项目「粘贴凭据即可用」的登录形态不兼容，详见 \`docs/recon/aliyun.md\`。

接口事实都记录在 \`docs/recon/\`，每份文档只写**实际观察到的东西**，
推断的部分会明确标注。

## 构建

推送到 \`main\` 或开 PR 会自动触发 \`.github/workflows/build.yml\`：

- \`test\`：13 个纯 JVM 模块的单测
- \`kernel\`：Rust 单测、clippy、交叉编译出 \`jniLibs\`
- \`android\`：等前两个 job 通过后，跑需要 Android 平台的单测（\`:app\`、\`:feature:shares\`、\`:feature:shareimport\`），再编译 debug APK

产物在 Actions 的 artifact 里（\`panhub-debug-apk\`）。
