# PanHub

一个统一管理多家网盘文件与分享的 Android 客户端。

- **Kotlin + Jetpack Compose** 写界面与业务
- **Rust** 写共享内核（摘要、分片校验等重活），通过 JNI 暴露窄接口
- **构建只在 GitHub Actions 上跑**，本地不编译

## 设计原则

1. **深模块化**：模块只通过窄接口交互。\`:core:*\` 是契约，\`:provider:*\` 是实现，
   \`:feature:*\` 是界面，\`:app\` 只做组装。新增一家网盘 = 新增一个 provider 模块
   + 一行注册，不动任何界面代码。
2. **能力声明而非类型判断**：每个 provider 声明 \`ProviderCapabilities\` 与 \`AuthMethod\`，
   UI 据此隐藏按钮、决定登录表单形态，杜绝 \`if (provider == "xxx")\` 这类耦合。
3. **错误归一化**：所有 provider 操作返回 \`PanResult\`，网络/鉴权/限流/不支持
   都映射成统一的 \`PanError\`，UI 只处理一种错误类型。
4. **UI 参考蓝云**：冷调蓝紫主色、浅冷灰背景、白色圆角卡片。

网盘内复制（`copy`）和「复制到其他网盘」是两件事：前者是同一个网盘里
再存一份，不需要下载再上传，因此只有拿到服务商自己的复制接口才声明
`capabilities.copy`。坚果云用 WebDAV 的 `COPY`（带 `Depth: infinity`，
目录会连子项一起复制）；百度与天翼用各自的文件管理接口。夸克、123 云盘与
蓝奏云没有做到可用的复制接口，界面会直接不显示这个入口。

夸克与 UC 是同一套 clouddrive 后端（`drive.quark.cn` 与 `pc-api.uc.cn`），
端点、字段、错误码都一样，差别只有主机名、`Referer`、风控参数 `pr` 与
`User-Agent`。所以两家共用一个 provider 实现，品牌差异收在 `CloudDriveBrand`
里——复制两千多行只为换四个常量，改一个字段就要改两遍，迟早只改对一半。
UC 侧用到的端点（`file/sort`、`file`、`file/rename`、`file/move`、`file/delete`、
`file/download`、`member`、`share`、`share/password`、`share/delete`、`task`、
`config`、分享的三个 `sharepage` 接口、上传的四个接口）在 UC 浏览器安装包里
都能逐字节搜到。

跨网盘转存不需要服务商提供额外接口：源端取下载直链、目标端走上传，
任何同时支持下载与上传的两个账号之间都能转存。中间文件落应用缓存目录，
传完即删。

「复制到其他网盘」的对话框里可以直接挑目标目录：默认存进对方根目录，
点子文件夹逐层往下走，换目标账号会回到根目录重新列。提交时带的就是
你选到的那一层——不用先复制到对方根目录再去对方账号里挪一次。

上传前的摘要计算走 \`:core:kernel\` 的 \`scan_file\`：一遍读盘同时算出整文件
MD5、SHA-1、前缀 MD5 与逐分片 MD5，四家网盘各取所需。没有 NDK 产物时
（本机调试构建）\`KernelUpload.scanner()\` 返回空实现，各 provider 自动退回
自己的 Kotlin 实现，所以「有没有内核」不影响正确性，只影响大文件的准备时间。

复制整个文件夹时，先在目标账号里按原层级把空目录逐层建出来，再把每个文件
当成一次普通的转存排进队列；目标账号必须支持新建文件夹。已经在目标端建好的
目录不会因为中途失败被回滚——目标端没有通用的批量删除，硬清理反而有风险。

下载整个文件夹时会先排一个「整理文件列表」的任务，把目录逐层列完再放出
每个文件的下载任务，本地按原来的层级还原（同名文件夹不会被摊平成一个）。

夸克网盘的上传走阿里 OSS：先向夸克要一张上传票据，把 MD5 与 SHA-1 报过去
（命中已有文件就直接秒传），再逐片换 OSS 签名往预签名地址 PUT，最后先合并
分片、再通知夸克索引。签名串多一个换行都会被判不匹配，所以那部分单独放在
`QuarkOss` 里并有逐字的单测。

夸克网盘的分享是异步的：创建接口只返回一个任务号，要轮询任务拿到分享
id，再换一次链接接口才有能发出去的地址与提取码。有效期服务端只有
永久/一天/一周/一月四档，用户选 3 天只能落到一周档，所以界面显示的是
实际到期时刻而不是用户填的天数。分享列表、取消分享也走同一套接口。

夸克网盘的「打开别人的分享」是一条独立链路：先用 pwd_id 换 stoken（分享的
访问票据），再按目录逐页读条目，每个条目额外带一个只对本次分享有效的
取件凭据；转存时把这些凭据和 fid 一起提交，服务端再起一个异步任务。
所以转存成败要轮询任务号才知道，完成数取服务端返回的 save_as 计数，
而不是请求里的条数——分享里的文件超过 100 个时，服务端只回前 100 个 fid。

123 云盘的「打开别人的分享」不需要先换票据：分享列表接口匿名就能读，
提取码直接作为参数带上（没有提取码时整段参数都不能出现，发空值会被判参数缺失）。
转存是登录后才能做的事，服务端只回一个任务号，要轮询到完成为止；
提交时每个条目都要带 `S3KeyFlag`/`Etag`/`StorageNode` 三样，
所以列表阶段就把它们拼成一个票据存进 `ShareEntry.ticket`。

123 云盘的分享列表还有个坑：`Next` 的终止值是字符串 `-1`，但空串表示「还有下一页」，
所以判断条件只能是 `!= "-1"`，写成 `isNotBlank()` 会永远停在第一页。

搜索框在 123 云盘上不是单独一个接口：它就是把普通列表请求里的 `searchData` 填上关键字，
再加一个 `isSearchOrder=true` 让服务端按相关度排序，`parentFileId=0` 表示不限目录。
关键字必须自己做百分号编码——表单编码会把空格变成 `+`，服务端当字面量加号处理，
带空格的关键字永远搜不到。搜索结果里的 `HighLight` 是带高亮标记的同一份文件名，
直接拿来当名字用，列表上会出现一堆标记串，所以仍然取 `FileName`；
它的 `ParentName` 会显示在结果行下面，三个同名文件不会只能挨个点开试。
搜索游标的终止值是 `-1` **和** `0` 两种（结果为空时是 `0`），只看 `-1` 会让结果页白翻一次。

从搜索结果的目录点进去时，目录栈会补一层「它原来在哪个目录」，
返回键先回到那个上级目录再一级级退，不会从深层目录一步跳回根目录。

顶栏标题下面有一行路径栏：账号名 / 一级 / 二级，点任意一格直接跳回去。
点一次只重新加载目标目录一次，不像连按返回键那样每退一级都拉一遍中间目录的列表。
路径只有一层时不显示这行——根目录本身没什么可跳的。

顶栏那个漏斗是「在当前目录里按名字筛」：只在已经加载的这一批里找，不发请求。
目录几百项时靠滚动找一个文件才是真的慢，而为一个临时查找去走跨目录搜索，
既慢又会撞上服务商限流，回来还可能是一堆同名结果。筛选中列表下面会写
「筛选中 3/120 项」，看清楚是筛掉了还是真没有。
进子目录、返回上级、跳路径栏都会顺手清掉关键字——
换了一个目录还留着旧关键字，打开就是一片空白，看起来像目录空了。
筛选中点「全选」只选看得见的那几条：把被筛掉的项目一起选中，
对这批文件执行删除或移动时会连没看见的东西一起处理掉。
预览的「上一张 / 下一张」也跟着筛后的顺序走，否则翻着翻着会跳到一张已经被筛掉的照片上。

系统返回键按「最临时 → 最持久」的顺序退：先退出多选，再收起筛选条，再返回上一级
目录，都没有了才离开浏览页。顺序反过来会让人以为选中的东西还在——
先退位置再退选择，屏幕上就只剩一个还亮着的选择状态，而选中的文件已经不在眼前了。

账号页顶栏的放大镜是「搜索全部网盘」：一次把关键字发给所有声明了搜索能力的账号，
结果按账号分组而不是混排——不同网盘的「相关度」根本不可比，混排出来的名次是假的，
而两个网盘里各有一个同名文件时，分组至少让「这是哪家的」一眼可见。
每家一次只带回来 100 条，服务端说还有下一页的账号会在列表底部出现「加载更多」，
并写明是哪几家还有——关键字宽的时候一家网盘就可能远超 100 条，
不给入口等于把后面的结果藏了；已经看过的那批不会因为翻页而换位置。
翻页时失败的账号保留原来的入口，一次超时不该让人只能从头再搜一遍。
一家网盘掉线只记在「这些账号没搜成」里，别家的结果照常显示——
失败要看得见，但不能让整次搜索看起来什么都没找到。
没有搜索能力的账号（坚果云、蓝奏云、天翼云盘）会列在结果下方说明它们没参与，
否则用户会以为自己漏看了。

「我的分享」页的漏斗是同一个筛选条：按标题过滤，没有标题时按链接尾段
（卡片上本来就显示那一串），所以照着屏幕上看到的字去搜一定搜得到。
它只在已经拉下来的那一批里找，不重新请求——分享列表一次只取 50 条，
关键字不该让服务端再跑一遍。分享列表通常只有十几条，所以筛选条默认收着。
一条都没有和被筛没是两件事：「还没有分享」提示去创建，
筛没了说的是「没有名字包含「…」的项目」并让人换个关键字。

回收站 123 云盘和百度网盘都接了。123 的删除接口是「放进回收站」（`file/trash`），
还原用的是同一个端点换一个 `operation`，彻底删除才是 `file/delete`。
这跟一开始写的实现不一样——最初文件列表里的删除直接打的是 `file/delete`，
也就是永久删除，点一次就找不回来了。
百度的回收站端点（`/api/recycle/list`、`restore`、`delete`、`clear`）
在安装包 dex 的字符串池里有，无凭证探测也能区分「端点存在」与「路径不存在」，
参数形状与开源客户端 cssxsh/baidu-client 一致，三方互证后才接。
夸克安装包里搜不到这类接口，它的回收站就先不做。

删除前会先弹一个确认框，正文随服务商是否有回收站而变：声明了 `capabilities.trash`
的（123、百度）写「会放进回收站的，之后可以还原」，按钮是「移入回收站」；
其余没有回收站的写「这个网盘没有回收站，删掉之后找不回来」，按钮是「永久删除」。
这段话是用户在按下按钮前唯一能依据的信息，所以宁可每次都问一句，也不默认用户记得这家有没有回收站。
还原失败有一种安静的情形要单独处理：原目录已经被删掉时服务端不报错，
而是在响应的 `data.AbnormalFileIdList` 里列出没还原成功的 id，
只看 `code` 会告诉用户「已还原」而实际有一项没动，所以这种情况会明确提示。
"还原"旁边那个按钮是"还原到…"：原目录已经不在时回原位置必然失败，
没有这个出口用户唯一的办法是先还原到一个不存在的地方再看着它失败。
它走 `file/recover/by_path`，请求体里的 `fileIds` 是**数字数组**——
网页端的 id 本身就是数字，写成字符串数组服务端会当成没给。

百度的回收站是另一套形状：条目用数字 `fs_id` 寻址而不是路径，
还原与彻底删除的响应 errno 为 0 时仍可能列着没成功的 id（`faillist`），
必须自己检查；它没有「还原到指定目录」的端点，只能回原位置，
所以「还原到…」入口对百度不显示，还原失败会明确提示而不是假装成功。
回收站里也有同一个筛选条，按名字过滤已经拉下来的那几页；筛着的时候
「全选」只选看得到的那些——这里按下去是「彻底删除」，把看不见的也圈进来太危险。

离线下载是「先解析、再挑选、最后提交」三步：解析把链接或磁力变成一份文件清单
（磁力只取 `xt=urn:btih:` 后面那段当 `info_hash`，普通链接走 `urls` 数组），
用户勾要存哪几个，再把资源号与文件号一起提交。
解析时外层 `code: 0` 不代表这一条成功，资源级 `err_code` 才是结果——
只看外层会把「这个链接不支持」当成「解析出来了，0 个文件」。
清单里的 `file_type` 是图标分类，不是「是不是目录」，拿它判断会把视频当文件夹。
提交时 `upload_dir` 是数字目录 id（`0` 是根目录），不是路径。
免费账号大概率会撞上「会员权限不足」（服务端 `code: 5250`），这个错误会照实显示出来。
离线下载目前也只有 123 云盘声明了能力，入口是浏览页的云朵按钮，存进你当时所在的那个目录。

提交成功的任务会列在同一页顶部：进度按服务端算好的百分比显示，下载中带实时
速度。列表只在进页面时拉一次，想看新进度点「刷新」——离线任务在服务端慢慢跑
就行，界面停一秒就多一秒轮询，不值得。删除只删任务记录，已经存进网盘的文件
不受影响。

收藏只有 123 云盘接了：`file/starred` 上的 `starredStatus` 不是布尔值——
`255` 是收藏、`1` 是取消，传 `true` 会被当成未知取值。
文件夹与文件都能收藏，收藏夹是跨目录的一份扁平清单（列表响应里没有路径），
所以从收藏夹点开一项时，会先回到它所在的目录再打开它，而不是在一个没有路径的列表里悬空。
收藏夹的列表接口与普通列表不是同一套字段：普通列表是 `InfoList` 加 PascalCase，
收藏列表是 `starredFileInfos` 加全小写驼峰，而且时间戳是**秒**而不是毫秒，
直接复用普通列表的解析只会拿到 1970 年的日期。
普通浏览页靠条目自带的 `StarredStatus` 决定要不要显示星标，不额外查一次——
列表响应本来就带着这个字段，为它多打一轮请求只是白白多一次等待。
多选之后底部操作条上也能批量收藏：一次请求带上所有 id（服务端收的就是数组），
目标状态按「是不是全都已经收藏过」定——全都收藏过就批量取消，混选时一律收藏，
因为用户做这个动作多半是想把它们攒起来，而不是因为第一个恰好收藏过就全取消。
底部操作条最多能有六个动作，所以改成等分宽度：按内容撑开会把最后一个挤出屏幕。
收藏夹里也有同一个筛选条，按名字过滤已经拉下来的那几页——
收藏夹是跨目录的，同一个名字可能出现在好几个文件夹里，靠翻页找太慢。
筛空了说的是要换关键字，和「这个网盘还没有收藏任何文件」分开说。

转存的目标目录默认是自己的网盘根目录，列表顶部那行「转存到 …」点开可以换。

### 本机文件

下载落在 App 私有目录里（不需要存储权限），传输列表清空之后这些文件仍然占着空间，
所以账号页顶栏有一个文件夹图标，进去是本机文件的完整清单。
它扫的是同一个目录，因此不会和传输页看到的对不上。
每一项可以打开（交给系统里能处理它的应用）、分享、另存到手机的其他位置，或者删掉。
删除只动本地这份副本，网盘上的原件不受影响；清空同理，只删文件不删目录本身。
下载攒到几十个之后靠滚动找人太费劲，所以顶栏有个筛选按钮：按名字过滤已下载的文件，
规则和网盘浏览页完全一样（忽略大小写、输入即筛、空词全留）。筛完一条不剩时说的是
「没有名字包含「…」的项目」而不是「本机没有文件」——磁盘上当然还有文件，只是名字都不匹配。
顶部那行「N 个文件 · 多少 MB」讲的是磁盘占用，不跟着筛选变，否则筛一半会让人以为少下了东西。
排序和筛选在同一个顶栏里：按名字、修改时间或大小排，再点一次同一个依据就反过来。
默认仍是「修改时间从新到旧」——这是本页一直以来的顺序，刚下完的文件在最上面；
没有修改时间的记录（系统读不到时间）排在最后，而不是当成 1970 年混进真实时间里。
先排后筛，所以筛选之后看到的仍然是同一个顺序。
另存走的是系统的「新建文件」对话框，所以由用户自己挑位置和文件名。
选目录用的是各家都有的普通文件列表接口（只看文件夹），所以三个支持转存的
服务商共用同一套界面；换目录是浏览过程中的一个短暂动作，用对话框而不是新页面，
取消之后还留在原来的分享目录里。

别的应用把链接分享过来时也能直接进这一页：PanHub 注册了 `text/plain` 的
`ACTION_SEND` 入口，出现在系统分享菜单里。分享过来的从来不是一条干净的链接，
而是「链接: … 提取码: a1b2 复制这段内容后打开手机网盘」这种整段话，
所以先用正则挑出第一个 http(s) 链接并截到空白或全角标点，再分别从链接的
query（`?pwd=`）和正文（「提取码」「密码」「访问码」）里找提取码，链接自带的那份优先。
链接填进去之后，连上账号就自动打开，不让用户对着一个已经填好的输入框再点一次。
只有纯文本分享会收：图片和文件分享过来我们没本事直接存进网盘。

天翼云盘的上传在另一条加密通道上（upload.cloud.189.cn）：每个请求都要把
表单做 AES-ECB 加密、再用 HMAC-SHA1 签名，随机密钥本身用服务端下发的 RSA
公钥加密后放进请求头。文件大于 10 MiB 时要额外报一个「分片摘要」——把每片
MD5 的大写十六进制用换行连起来再取一次 MD5；服务端据此判断能否秒传。
细节在 docs/recon/cloud189.md，纯字符串与摘要逻辑有单测。

官方客户端还有一条自己的通道（api.cloud.189.cn），每个请求都用
sessionSecret 做 HMAC-SHA1 签名，不需要 Cookie。这条通道在项目里已经实现成
可插拔的一层，但**默认不启用**：换会话与刷新 token 都要真实 accessToken 才能
验证，没有账号时切过去只会把现在能用的 Cookie 通道弄坏。预留层把「换会话 /
刷新 token / 签名请求 / 会话失效自动重试一次」四件事都写好并用脚本化响应测住，
将来有账号时只要把 provider 的调用点换过来。

百度网盘的上传要报三个摘要：整文件 MD5、**前 256 KiB** 的 MD5、以及每片的
MD5 列表。分片字节走 d.pcs.baidu.com 的 superfile2（域名由 locateupload
换发，这个接口不需要认证），收尾再由 xpan/file 的 create 合并。秒传判定在
precreate 的 return_type 里，等于 2 就直接拿到文件元数据。分片大小按非会员的
4 MiB 切，会员账号同样可用，只是片数更多。

上传整个文件夹是同一套思路反过来：先在网盘里按本地层级把目录建出来，
再把每个文件当成一次普通上传排进队列。空文件传不上去，会在整理阶段跳过
并在进度里写明跳过了几个；整棵树都是空文件时会说清楚是「空文件夹（跳过
N 个空文件）」，而不是假装什么都没发生。

上传之前会先在当前目录里查一遍重名：有同名的文件就先把队列停住，
说清楚「继续上传后，有的网盘会覆盖旧文件，有的会自动改名，由网盘自己决定」，
按钮写「仍然上传」而不是「确定」。各家对同名的处理并不一致，覆盖意味着原文件消失，
这一步不问，用户就永远不知道自己刚才顶掉了什么。没重名就直接入队——
绝大多数上传都不撞名，每次都弹框只会让人学会闭眼点确认。比对按字符串严格进行，
`a.txt` 与 `A.txt` 不算重名：多数网盘里它们本来就是两个文件。
只比对当前已加载的这一批，还没翻到的部分看不见，所以话术不假装知道全部。

传输期间会起一个前台服务（dataSync 类型），通知栏常驻一条进度，
说的永远是「现在在传什么、还剩多少」。它的作用不是好看：手机上的后台
进程随时会被回收，几 GB 的下载传到一半被杀掉，用户回来只看到队列卡住。
只在队列里有活的时候启动，传完自己停，不会留一个空壳在后台。

一轮任务全部结束时另发一条可以划掉的通知：「传输完成 · 3 项完成 · 12 MB」，
有失败就写「传输结束，有 2 项失败」。它只数这一轮真正跑过的任务——冷启动从存档
恢复出来的历史任务早就结束了，算进去会让人在什么都没做的时候收到一条「传输完成」，
然后就再也不想看到这个通知了。取消的任务不算失败：那是用户自己不要的。

传输遇到断网、限流、服务端 5xx 会自动重试（默认 3 次，1 秒起翻倍退避），
退避期间任务让出队列，后面的文件可以先传。鉴权过期、文件不存在这类
重试无意义的错误直接失败，让人早点看到真正的原因。

传输队列会存档：进程被杀掉、手机重启之后队列还在，上次没跑完的任务自动接着跑
（下载靠 `.part` 续传，上传与转存重来一遍）。存档坏了只会丢掉历史，不影响启动。

下载断点续传：没下完的文件留在 `.part` 里，下一次用 `Range` 只补剩下的部分。
服务端忽略 `Range` 回 200 时不会把整份内容追加到旧残片后面（那样文件就毁了），
而是从头写；残片比目标还大则直接丢掉。只有「区间不存在」（416）才认为是链接失效，
丢掉残片重来，网络错误一律保留残片等下次。


传输页标题会带上整体进度：队列里有几项在跑、已经搬完多少字节、大概到几成。
没有总数（比如上传时还不知道目标端要写多少）就只显示任务数，不编一个百分比出来。

正在传的那一项会显示实时速率和剩余时间，速率按最近 5 秒的采样算。
速率要至少两个采样点、跨度满 0.5 秒才报，刚起步的瞬间什么都不显示
（写「0 B/s」会让人以为卡住了）；排队中的任务、已经结束的任务、以及只搬列表的
整理型任务都不显示速率。剩余时间向下取整，宁可说少了也不让人以为还要等更久。

传输页顶栏在有失败任务时会出现「重试失败」，一次把失败的任务都排回队列。
取消的任务不算在内——那是用户自己不要的，批量重试不该把它捡回来。

顶栏的筛选按钮会拉出「按名字筛选」：队列跑久了会有几十条任务，靠滚动找某一条最费劲。
它和上面的「全部 / 进行中 / 已结束」是两层：标签先说看哪一类，关键字再在结果里找名字，
两个都只收窄不改变顺序，也不发请求——任务名早就装在内存里了。
规则与浏览页、本机文件页共用同一份实现，同一个手势在三页表现必须一致。
列表空着时有三种说法：队列本来就空、这个标签下没有、关键字筛没了。
混成一句「还没有传输任务」会让明明有五个失败任务的用户以为记录丢了。

正在传和排队中的任务都能暂停，暂停之后可以继续。暂停与取消的差别只在磁盘上：
取消会把没下完的 \`.part\` 删掉，暂停留着它——下次继续时用 \`Range\` 接着传，
不用从头再来。暂停的任务不占执行位，队列里后面的任务会顶上来；
它保留原来的位置和已传字节数，恢复时不会跑到队尾，也不会显示成从零开始。
正在退避等待重试的任务同样能暂停，那个计时器会一起停掉，否则几秒后它自己又跑起来了。

排队中的任务卡片会显示「前面还有 N 个」，并且有一个「优先」按钮把它挪到队首。
队列是串行的，排了十个文件之后突然要某一个先传，以前只能全部取消重排。
置顶只改顺序，不动任务状态：已经下好的 `.part`、已经算过的重试次数都还在，
暂停中的任务挪到前面也仍然暂停——置顶不是「继续」。正在跑的和已结束的没有这个按钮。
位置是在整条队列里数的，不是在当前筛选出来的列表里——切到「已结束」时
前面的排队任务会被筛掉，那样数出来的位置是假的。

传输页是唯一把不同账号的任务混排在一起的地方。多账号时，任务卡片的状态行会带上
账号名（优先用备注名），跨网盘转存显示成「A → B」——只说源端会让人以为文件是
下到 A 里去了。只有一个账号时不显示：每张卡片都重复同一个名字是纯噪声。
账号已被删掉的任务显示「未知账号」，而不是留一段空白让人猜。

下载好的文件在传输卡片上还能「另存到」别处（右上角的保存图标）。下载落在应用
私有目录里，卸载 App 就一起没了；分享只是借别的应用的手转存一份。系统提供的
「保存到…」才是把这个文件真正交给用户自己管——位置由用户挑，可以是手机存储、
SD 卡或者某个文档提供者。只有真正下载下来的文件才有这个入口：转存任务的本地
路径是中途用的临时文件，上传任务的路径是用户自己的源文件，另存它们都没有意义。

清空传输列表只是不再显示，文件还在应用私有目录里占着空间。所以下载完成的任务
卡片上另有一个删除按钮，删的是磁盘上那个文件；删掉之后任务记录还在，只是不再指向
任何文件。上传任务没有这个按钮——它的本地路径是用户自己挑的源文件，照着删等于毁数据；
转存任务的路径是中途用的临时文件，完成后早就不在了。

阿里云盘按设计不接入：两条接口路线分别要开放平台密钥和设备签名，
与本项目「粘贴凭据即可用」的登录形态不兼容，详见 \`docs/recon/aliyun.md\`。

每个账号可以起一个备注名（卡片右侧的铅笔）。同一家网盘挂了两个账号时，
备注名比服务商给的昵称好认；起了备注之后，真名下移到第二行的开头，
所以「这是哪家的哪个号」一眼都在。备注名纯本地，不发给服务商也不同步，
只留第一行、连续空白压成一个空格、最长 24 个字——粘贴一整段话进来也只取第一行。
清空备注等于从未起过，界面退回显示服务商的昵称。

夸克、UC、百度三家不用再手抄 Cookie：点账号页里的对应网盘，会弹出内嵌的
官方登录页（夸克/UC 是 CAS 页，百度是 wappass 移动页）。这与官方 App 的
登录方式一致——官方客户端本身就是 WebView 开这些页面再把 Cookie 交给
原生层（取自反编译出的 dex，见 docs/recon）。Cookie 齐了（夸克/UC 看
kps/ppu，百度看 BDUSS）就自动提交，走的是和粘贴 Cookie 相同的验证链路。
123 与坚果云维持原样：前者官方就是账密登录，后者走 WebDAV 应用密码。


Cookie 是有时效的：过期之后不用删掉账号重新加一遍——账号卡片上有一个「更新登录」按钮（登录图标的那个），把新的 Cookie 粘进去提交就行。新凭据先在服务商那里验证，验证通过只换凭据本身：账号的标识、备注名、创建时间都保持原样，传输记录和各个入口不会因为换了 Cookie 而失联。如果新凭据验出来是另一个账号（比如换了用户名），App 会拒绝并提示删除旧账号重新添加，而不是把两个账号搅在一起。

账号卡片上会显示每个网盘已用多少、总共多少（蓝云那种细容量条）。
容量是装饰性的：不支持容量查询的网盘不显示，查询失败也不弹错误、不挡住列表，
每个账号只试一次——失败的多半是凭据过期或服务商不认，每次刷新都重试只是白费流量。

接了两个以上网盘时，列表最上面多一张「全部网盘」的卡片，把各家的已用加起来。
它只加那些真的报了总容量的服务商：把「不知道总量」当成 0 会让总和凭空变小，
看起来像空间被谁吃掉了一块，所以有几家没给总量时会在后面写明，并且不报百分比。
这里刻意不画汇总条图——各家的「总量」含义并不统一（有的含回收站、有的算上家庭空间），
把它们的比例叠在一起画会暗示一种并不存在的可比性。

外观可以在账号页右上角的齿轮里改：跟随系统、固定浅色、固定深色。
选了就立刻生效并写进 `settings.json`，没有「保存」按钮——外观是开关不是表单。
“跟随系统”会实打实地跟着系统变，包括系统按日落自动切换的那种，
所以三个选项而不是一个“深色”开关：只有一个布尔就再也回不到跟随模式了。
设置文件读坏了按默认值处理，与队列存档同一个理由：存档是给人方便的，
不是真相源，一个解析不了的旧文件不该让 App 打不开。

同一页里还有「存储」：那一行显示上传副本与跨网盘中转临时文件一共占了多少，
点一下清掉。它只认这两处（`cacheDir/upload` 与 `cacheDir/cloud-copy`）——
上传前会把选中的文件复制一份到应用缓存，跨网盘复制也要先落一份本地再传；
这两处此前没人清理，越用越大。「清理缓存」刻意不含下载目录、账号、
传输队列与设置：那些是用户的东西，清缓存不该顺手把它们删了。
目录本身保留不删，下次上传还要往里写。

同一页里还有「仅 Wi-Fi 传输」。打开之后，移动数据下排队的任务一个都不开始，
传输页顶部会写明是被这个开关挡住的；连上 Wi-Fi 的瞬间队列自己接着跑，
不用重开 App、也不用再点一次。

这道门只挡“开始”，不打断已经在跑的：跑到一半从 Wi-Fi 掉到移动数据时，
硬砍正在传的文件会留下半截残片，而且用户往往就是刚刚才换的网络。
门后面的理由（现在该不该传）与判断网络类型的地方是分开的——队列是纯 JVM 模块，
让它认识 `ConnectivityManager` 就等于把它拖进平台层，测试也得跟着起 Robolectric。

图片和文本可以在浏览页里就地看一眼（右侧菜单里的「预览」），不用先下载。
只支持这两类：它们是对话框里就能画出来的东西；PDF、音视频要交给系统应用打开，
那属于「下载」而不是「预览」，放进来只会多一个含糊的入口。

预览只读文件开头一段（图片 12 MB、文本 256 KB），超出的部分不读，
并在界面上说明「内容较长，这里只显示了开头一部分」——为了一眼把 200 MB 的日志
整个拉下来既费流量又转很久。读取时带 \`Range\`，服务端支持就只传前一段，
不支持也只是多读了这么多。类型判断先信 MIME 再信扩展名：服务商把 \`.md\` 标成
\`application/octet-stream\` 很常见，只信 MIME 会让一批文本文件没有入口。

同一目录里还有别的图片（或别的文本）时，预览框右下角会出现「上一张 / 下一张」，
标题旁边标着「3 / 8」。翻页只跟同一类文件互相翻：在十几张照片里夹着一个
`.md`，翻到它再翻回来只会打断浏览。当前文件不在这个目录的列表里时
（从搜索结果、文件详情打开的），两个按钮都不出现——这种时候「上一个是谁」
根本没有答案，宁可不猜。

图片还能放大看：捏合可以连续缩放，双击在「放大」和「原大」之间切换，
放大之后可以拖动，拖到边就停住不会甩出框外。倍数夹在 1 到 4 倍之间——
再往小只是把图缩成一个小方块，再往大就只剩马赛克。放大状态下多一个
「还原大小」按钮，不是每个人都知道双击能还原。

图片和视频的列表项直接显示服务商返回的缩略图（百度、天翼、123 云盘的列表
响应里带缩略图地址），加载失败或没有就退回类型图标——不单独报错，缩略图
只是锦上添花。夸克、UC、坚果云与蓝奏云的列表响应不带缩略图地址，它们的
列表始终用图标。

接口事实都记录在 \`docs/recon/\`，每份文档只写**实际观察到的东西**，
推断的部分会明确标注。

## 构建

推送到 \`main\` 或开 PR 会自动触发 \`.github/workflows/build.yml\`：

- \`test\`：14 个纯 JVM 模块的单测
- \`kernel\`：Rust 单测、clippy、交叉编译出 \`jniLibs\`
- \`android\`：等前两个 job 通过后，跑需要 Android 平台的单测（\`:app\`、\`:core:platform\`、\`:feature:accounts\`、\`:feature:browser\`、\`:feature:settings\`、\`:feature:shares\`、\`:feature:shareimport\`、\`:feature:transfers\`、\`:feature:search\`、\`:feature:trash\`、\`:feature:offline\`、\`:feature:starred\`、\`:feature:localfiles\`），再编译 debug APK

产物在 Actions 的 artifact 里（\`panhub-debug-apk\`）。
